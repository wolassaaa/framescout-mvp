# FrameScout Session 全选与策略化 AI 审阅设计

日期：2026-07-14  
状态：待用户书面复核  
适用范围：Web 主界面的审阅台、网格、标签显示与本地/云端 AI 分析链路

## 1. 目标

本次改动解决四个直接影响选片效率的问题：

1. 在当前项目 session 的当前筛选结果中，一键勾选全部照片；
2. 明确区分 AI 已处理、AI 建议和人工决定；
3. 允许摄影师选择按 AI 结果审阅、全部重审或专查 AI 淘汰；
4. 让本地和云端模型先读出统一视觉信号，再由同一审查策略执行“符合则留，不符合则淘汰”。

本设计借鉴 Lightroom 的当前视图全选、旗标和属性筛选，以及像素蛋糕的批量操作、AI 标签可见和保留人工标签原则。它不复制视觉外观，继续采用 FrameScout 的深色、高密度、键盘优先工作台。

## 2. 核心概念

### 2.1 Session

当前 session 是当前打开的 FrameScout 项目。全选不会跨项目，也不会访问另一个文件夹或历史项目。

### 2.2 当前筛选结果

全选作用于用户当前看到的逻辑集合，而不是当前 DOM 中已经渲染的缩略图：

- 审阅台：当前审阅模式、AI 状态筛选、标签筛选和当前分组共同得到的全部资产；
- 网格：当前左侧筛选、标签搜索和当前分组共同得到的全部资产；
- 即使网格只渲染前 240 张，符合条件的第 241 张以后也必须被勾选。

### 2.3 批量勾选与人工决定

批量勾选是临时工作集合，和人工决定完全分离。

- `全选` 只向批量勾选集合加入资产 ID；
- `取消全选` 只清空当前筛选结果中的勾选；
- 全选不会自动设置精选、候选、保留观察、淘汰或标签；
- 后续批量决定和批量标签必须由用户再次明确触发；
- 切换页面时，同一 session 的勾选集合在审阅台和网格之间共享。

## 3. 交互设计

### 3.1 共享选择栏

审阅台和网格都显示同一组紧凑操作：

- `全选` / `Select all`；
- `取消全选` / `Clear selection`；
- `已勾选 N 张` / `N marked`；
- 当前结果全部勾选后，`全选`显示为选中状态；
- 没有匹配资产时禁用全选。

标准快捷键：

- `Ctrl+A`：勾选当前筛选结果中的全部照片；
- `Esc`：清空批量勾选；
- 输入框、下拉框和标签编辑器获得焦点时不拦截快捷键。

审阅台胶片条和网格缩略图使用同一种勾选描边与角标。当前主图仍是单张活动照片，不能因为批量勾选而失去当前焦点。

### 3.2 AI 星标

每张缩略图底部显示一个小型 AI 状态标记：

- 绿色星：AI 已处理，结论为 `keep`；
- 黄色星：AI 已处理，结论为 `review`；
- 红色星：AI 已处理，结论为 `reject`；
- 无星：没有任何持久化 AI 证据，尚未处理；
- 分析失败不能显示为已处理。

星标不是 Lightroom 人工评分，也不修改人工决定。悬停或键盘聚焦时显示：

- 当前策略的中英文名称；
- 模型和版本；
- AI 结论；
- 最高优先级原因和置信度；
- 降级或能力缺失状态。

### 3.3 审阅模式

审阅台和网格提供一致的三段模式控制：

1. `按 AI 结果` / `AI assisted`：显示绿色和黄色资产，默认隐藏无人工作决定的红色资产；
2. `全部重审` / `Review all`：显示全部资产，忽略 AI 隐藏规则，但保留星标作为参考；
3. `检查 AI 淘汰` / `Audit rejects`：只显示红色资产，用于检查误杀。

额外筛选项：

- `AI 已审` / `AI reviewed`；
- `等待 AI` / `Awaiting AI`；
- `建议复审` / `Needs review`。

模式和筛选只改变可见集合，不修改 AI 或人工数据。

## 4. 中英文与标签

中文为默认语言，英文完整保留。项目、导入、分析、审阅台、网格、标签、导出、设置和提示状态全部使用结构化文案表，不允许在组件内继续新增硬编码可见字符串。

机器标签使用稳定英文键，显示文本本地化：

```text
subject:person  -> 人物 / Person
object:car      -> 汽车 / Car
scene:empty     -> 空镜 / Empty scene
quality:soft    -> 模糊 / Soft focus
ai:reviewed     -> AI 已审 / AI reviewed
```

规则：

- 数据库、筛选和导出合同使用稳定键；
- UI 根据语言显示中文或英文名称与注释；
- 用户手写标签保留原文，不自动翻译或改名；
- CSV/XMP 默认导出稳定键，后续可另加本地化展示列；
- 未知机器标签回退显示原始键，不能显示空白。

## 5. AI 架构

采用“视觉感知提供者 + 策略判定器”两阶段结构。

### 5.1 视觉感知提供者

本地 YOLOX、本地视觉语言模型和云端视觉 API 都输出同一份标准信号：

- 检测到的主体、对象和场景标签；
- 主体与全局清晰度；
- 曝光与可读性；
- 人脸、闭眼和表情能力状态；
- 构图、空镜、运动模糊等可用语义；
- 每个信号的置信度、模型、版本和能力状态。

提供者不能直接写人工决定。提供者无法理解策略所需语义时必须报告 `unavailable`，不能伪造零检测。

### 5.2 策略判定器

策略判定器读取 `strategies/*.strategy.json` 和标准信号，输出：

- `keep`：满足策略要求且没有硬失败；
- `review`：证据不足、冲突或模型能力缺失；
- `reject`：明确违反策略中可测试的淘汰规则，并满足硬淘汰证据要求。

同一信号在不同策略下可以得到不同结果。例如没有人物的场地全景在“赛事故事”中可保留，在严格“人物精选”中可进入复审或淘汰。

### 5.3 本地和云端一致性

- 本地模型与云端 API 共用策略判定器；
- 云端模型主要负责产生语义信号，不独立解释最终淘汰政策；
- 云端只接收用户明确授权的缩小代理图，永不上传 RAW；
- 当前 YOLOX 能力不足以判断复杂内容时只能输出黄色复审；
- 后续接入本地视觉语言模型时不改变 UI、数据库或策略文件格式。

### 5.4 人工优先

- 重新分析只更新 AI 证据、星标和 AI 结论；
- 不覆盖人工决定或人工标签；
- 不删除、移动或修改源照片；
- AI 红星必须始终可恢复和审计。

## 6. 数据流

1. 用户选择策略和模型配置；
2. 本地服务读取分析代理图；
3. 感知提供者输出标准视觉信号；
4. 策略判定器生成 AI 结论、原因和标签；
5. SQLite 原子写入信号和本次分析运行记录；
6. React 读取持久化证据并派生星标状态；
7. 用户选择审阅模式、筛选并全选当前结果；
8. 只有明确的后续按钮才会批量应用人工决定或标签。

## 7. 错误与资源边界

- 全选只存资产 ID，不复制图片、Blob 或缩略图数据；
- 对 5000 至 10000 张照片，全选时间应与 ID 数量线性相关且不触发图片解码；
- 分析中的照片保持无星或显示独立进度，不提前显示成功；
- 失败或取消的分析不能留下伪造的已审星标；
- 策略文件无效时阻止启动分析并显示具体校验错误；
- 模型不可用时进入复审降级，不自动硬淘汰；
- 所有源照片保持只读。

## 8. 验收标准

### 8.1 选择

- 当前筛选命中 1000 张、只渲染 240 张时，全选后计数为 1000；
- 审阅台全选后进入网格，仍显示相同勾选集合；
- 全选不改变任何 `humanDisposition` 和标签；
- 切换筛选后，取消全选只清除当前结果，不误清其他集合；
- `Ctrl+A` 与按钮结果一致。

### 8.2 AI

- 有持久化证据的资产显示与结论一致的星标；
- 没有证据、分析失败或尚未运行的资产不显示星标；
- 三种审阅模式产生正确集合；
- 同一标准信号通过不同策略得到可预测的不同结论；
- 能力缺失不能产生错误红星；
- AI 重跑不覆盖人工决定和人工标签。

### 8.3 本地化与视觉

- 中英文下所有新增按钮、筛选、提示、标签名和工具提示完整；
- 1280x800、1440x900 和 120% UI 缩放下无文字重叠；
- 星标、批量描边和人工决定颜色可同时辨认；
- 键盘操作有可见焦点状态。

### 8.4 自动化

- reducer 单元测试覆盖跨 240 张批次的全选和局部取消；
- Python 策略测试覆盖正例、反例、冲突和能力缺失；
- Rust 合同测试覆盖运行状态与持久化证据；
- Playwright 覆盖审阅台、网格、双语、双视口和全选后批量动作；
- 真实图片测试保持源目录哈希和修改时间不变。

## 9. 非目标

- 本阶段不让 AI 自动写人工精选或人工淘汰；
- 不训练个人审美模型；
- 不删除源照片；
- 不把 AI 星标伪装成 Lightroom 1 至 5 星人工评分；
- 不在本阶段实现人脸身份命名或云端人物库。
